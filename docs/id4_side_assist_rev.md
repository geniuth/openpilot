# MEB_Side_Assist_02 (0x24D) 후측방 코너레이더 리버싱 — 진행 기록

ID.4의 후방 코너레이더 2개(Side Assist)는 가공된 경고 신호(`MEB_Side_Assist_01`,
0x24C)만 DBC에 있고, 원시 타겟 데이터로 보이는 `MEB_Side_Assist_02`(0x24D)는
미해독이다. 이걸 풀면 차선변경 안전 게이트 → 추월 제안 기능의 전제가 된다.
분석 도구: `openpilot/selfdrive/debug/vw_meb_side_assist_scan.py` (rlog 입력).

참고: ID.4에 **전방 코너레이더는 없다** (전방 레이더 1 + 후방 코너 2 구성).
전방 레이더 원시 타겟은 `Strukturen_01`(0x24F)로 이미 해독·사용 중이다.

## 확정/후보 필드

1차: 2분 주행 rlog + 핸드오프 대조. 2차: 정차+우측 통과 rlog 3세그먼트
(실제로는 저속 주행 구간 포함 — 이게 결정적이었다).

| 슬롯 b2 | 0 부근 부호형 소값 — 변화율(rate) 계열 후보 | 미확정 |

## 좌측 데이터의 소재 — 미해결 (0x183 후보는 폐기)

0x183은 DBC 대조 결과 **MEB_Camera_01(순정 전면 카메라 출력)**로 판명 — 좌측
후측방 레이더 후보에서 제외 (0x234도 MEB_Camera_02). 이들 바이트가 좌측 BSM과
동기화된 건 추월 완료한 차가 전방 좌측에 나타나 카메라 물체 리스트에 잡히는
간접 상관으로 보인다. 남은 가설: 후측방 레이더 2개 중 한쪽이 마스터로, 좌측
센서는 프라이빗 링크로 마스터에 붙고 0x24D 한 메시지에 양쪽이 다 실리거나
(헤더/슬롯 어딘가에 좌우 구분), 좌측 원시 데이터는 이 버스에 아예 안 나온다.

## 검증 방법

- **핸드오프 대조** (1차): 추월차가 후측방에서 사라지고 0.9~2.8초 뒤 전방 레이더
  (해독 완료된 정답지)에 나타난 3건 대조 — 다만 [b5,b6] 속도 해석은 2차에서 기각됨.
- **자차 속도 상관** (2차): 이동 구간에서 필드~vEgo 상관 + 필드 미분~vEgo 상관으로
  속도/위치 필드를 분리 시도. 슬롯이 FF로 안 비워지고 다른 물체를 이어받는
  "슬롯 재사용" 때문에 긴 run 통계는 오염됨 — b4 전환/바이트 점프로 물체 세그먼트
  분리가 필수.
- **BSM 정답지 대조** (2차): 0x24C의 Info_Right/Left 상승 에지 시각에 근접 타겟과
  헤더 변화를 대조.

## 남은 것

1. **거리(range) 필드 발견** — 현재 최대 미해결. 방법: 추월차가 후측방에서 소멸한 직후
   전방 레이더(Strukturen_01, 거리 해독 완료)에 등장하는 핸드오프 시점의 기하로,
   소멸 직전 프레임에서 "알려진 거리"에 대응하는 비트 패턴을 역추적. 비트 경계를
   1비트 단위로 훑는 스트래들 탐색 필요.
2. b3=방위각 확정 — 방위각이면 tan(b3)·range = 횡거리로 차선 판정 가능.
   깨끗한 고속 추월(등속) 트랙에서 b3(t)가 arctan 모델에 맞는지 피팅.
3. 좌측(0x183) 구조 해독 — 뒤쪽 4개 8B 그룹(끝바이트 0x11 마커) 중심으로.
4. **주행 조건**: 60km/h 이상 정속(간선/고속도로)에서 추월당하는 장면 다수 —
   저속 시내는 트랙이 짧고 지저분함. 정차는 무용(저속 블랙아웃).
5. 이후 활용 순서: 차선변경 안전 게이트 → comma 화면 후측방 트랙 시각화
   → 추월 제안. (자동 깜빡이는 불가 — 방향지시등 CAN 발신은 안전상/구조상 막혀 있음)

## 참고: HKG 대비

현대기아는 후측방 레이더 SCC 메시지가 커뮤니티에서 이미 해독돼 carrot의 코너레이더
기능(EnableCornerRadar)이 그걸 쓴다. MEB는 우리가 처음 푸는 것이라 위 과정이 필요하다.

## 3차 (opus 재분석): 슬롯 필드 3개 확정 — 정지물 대조 + 전방레이더 핸드오프

전방 레이더 liveTracks(해독 완료 정답지)와 정지물(가드레일=속도0)을 앵커로,
0x24D 8B 슬롯(byte16~63, 6슬롯)의 필드를 재검증. **2차의 "b5,b6 속도 기각"을 정정** —
속도가 맞다. 기각했던 이유(고속도로 트래픽이 자차와 같은 속도라 상수처럼 보임)가
오히려 반증: 정지물을 보면 0을 읽는다.

### 확정 (슬롯 오프셋은 byte 기준, 슬롯 내 0~7)

- **byte5~6 (LE, ×0.01) = 타겟 절대 지면속도 (km/h)**. 정지물(가드레일/기둥)=0~8,
  주행 트래픽=73~85. 7개 세그먼트 일관. ← 2차 기각을 뒤집는 핵심.
- **byte4 = 물체 종류**: **0xFF=정지물(가드레일 등)**, **0x_7(0x17/0x27/0x37)=이동 차량**.
  정지=0xFF 100%, 이동=0xFF 0%. 상위니블(1/2/3)은 좌/우존 또는 품질 후보(미확정).
- **byte2 = 부호형 종방향 접근값**: +=뒤, 0=나란히, −=앞. 추월 시 +88→0(나란히)→−2로
  단조 감소하며 0을 통과(seg11 자차15/타겟85 추월에서 뚜렷). 단 **선형 미터는 아님**
  (접근속도로 미분 시 스케일 0.5~3.7로 불일치 — 근접/경고 인코딩으로 추정).

### 미확정 / 남은 것

- **좌/우 판별 (BSM 핵심)**: byte4 상위니블(1/2/3), byte3(방위각 후보, 이동 시 노이즈
  180~201), 슬롯 인덱스(0~5)가 좌/우와 어떻게 매핑되는지 미확정. 필요 데이터:
  **좌·우 양쪽 추월이 다 든 rlog** (현 로그는 대부분 한쪽). 전방레이더 yRel 부호로
  자동 라벨 가능.
- **선형 거리(m)**: byte2가 비선형이라 별도 필드 필요 — 미발견. 다만 BSM 경고엔
  byte2(나란히 통과 감지)+byte5,6(속도)+byte4(차량 필터)로 충분.
- byte0(정지물≈50, 이동148~199), byte1/byte7=0x80 상수(부호/플래그 추정).

### 실용 관점

블라인드스팟 경고의 최소 요건은 이미 갖춰짐: **byte4로 차량만 필터 → 슬롯 점유 →
byte2가 0 부근(나란히) → byte5,6로 접근속도**. 남은 건 좌/우 배정뿐 — 양측 추월
데이터만 있으면 차선 때처럼 앵커링으로 확정 가능.

## 4차 (fable 검토): 3차 결론 대폭 정정

3차(opus)의 확정 주장들을 재검증한 결과:

- **byte5~6=절대속도 — 기각.** 16개 세그 전수 히스토그램에서 이동클래스(b4=0x_7) 값이
  **전부 83~86.2**에 갇힘 (min83/max86.2, n=25,693). 자차 12km/h 정체 시내에서도 85를
  읽음 — 속도일 수 없다. 3차의 "타겟 32/60km/h" 근거는 슬롯 재사용 오염(유휴 4↔이동 85
  혼합 런 평균)이었음. 구조상 b6 상위니블(0x2_)=활성 플래그, 하위 12비트(bit40|12)가
  실제 변수(추월 중 199→402 단조증가, 의미 미확정 — 각도/근접도 후보).
- **b4=0xFF "정지물" — 재해석.** 0xFF 행의 꼬리 `fec8ffa101`이 서로 다른 도로에서
  완전히 동일 → 물체 측정값이 아니라 **유휴 슬롯 채움 패턴**. 0xFF=유휴(비활성 변형),
  0x_7=활성 트랙. "정지물=속도0" 증거도 이에 따라 무효.
- **b2=부호형 접근값 — 방향성 생존.** seg11 추월 +88→0→−2 단조 제로크로싱은 유효.
  핸드오프 라벨과 부호 일치(추월당한 직후 −소값 / 추월한 직후 +값 = +뒤/−앞).
  선형 미터 아님(스케일 불일치)도 유지.
- **좌/우 — 여전히 미확정 + b4 니블(1/2/3) 후보 탈락.** 좌측 추월(seg11, 전방 y=+5.8
  핸드오프)과 우측 추월(0385 33.2s 영상앵커) 모두 b4=0x27 — 같은 값이 양쪽에서 나옴.
  전방레이더 핸드오프 자동수확(좌18/우6건)에서도 단일 바이트 분리 실패.

남은 순서: ① 유휴패턴 필터 강화 후 핸드오프 수확 재실행(라벨 오염 제거),
② bit40|12 필드의 물리 의미(각도?) 규명 — 각도면 부호/구간으로 좌우가 나올 수 있음,
③ 좌·우 양측 추월이 고루 든 60km/h+ 정속 주행 데이터로 확정.
