# Kia Soul EV (KIA_EV_SK3) 조향 풀림 — 심층 근본원인 분석

> 원칙: 지금까지의 실차 로그 + 코드(carrot-wip 기준)로 검증된 사실만. 추정은 "가설"로 명시.
> 결론 먼저: **현재 로그만으로는 근본원인을 단정할 수 없다. 단, 로그가 심하게 "오염(confounded)"되어 있어 그게 1차 문제다.** 깨끗한 1개 실험으로 분리 가능.

---

## 0. 코드로 확정된 사실 (high confidence)

| 항목 | 사실 |
|---|---|
| 플랫폼 | `KIA_EV_SK3`, flags = `CHECKSUM_CRC8 | EV`, non-CAN-FD, 토크식 MDPS, DBC `hyundai_kia_generic`, harness hyundai_c |
| LKAS11 체크섬 | `CHECKSUM_CRC8` 경로 정상(`hyundaican.py`: crc8, init 0xFD, xor 0xDF). **체크섬이 틀리면 100% 먹통이어야 하는데 평소엔 조향됨 → 체크섬은 정상.** |

| MDPS 미작동 | 풀림 구간엔 `CF_Mdps_ToiActive=0`(MDPS가 토크 미적용). 폴트 플래그(`ToiFlt/Unavail`)는 0(정상시). |
| `steerFaultTemporary` | `= CF_Mdps_ToiFlt or ToiUnavail`. **1이 되면 controlsd가 `latActive=0`로 횡제어를 끔**(`controlsd.py:124`). |
| `CF_Lkas_ToiFlt` 송신 | OP가 `torque_fault = latActive and not apply_steer_req`를 매 프레임 LKAS11에 실어보냄. `>85°` 처리(common_fault_avoidance)가 이미 이걸 토글함. |
| **내 시도(철회됨)** | 저각도에서 요청비트를 끊자 `CF_Lkas_ToiFlt=1`→이 MDPS가 `CF_Mdps_ToiFlt=1`로 폴트→`latActive=0`. **요청비트/ToiFlt 토글은 이 MDPS에 독.** 전량 revert. |

## 1. 로그 해석의 결정적 함정 — 데이터가 오염되어 있다

지금까지 받은 "조향 풀림" 로그의 **공통 조건**을 정리하면:

| 로그 | 속도 | 운전자 입력 | ToiActive |
|---|---|---|---|
| 최초 로그(정상 조향 관측) | **11~12 m/s (~40km/h)** | 손 거의 뗌 | **1 (정상 작동)** |
| 이후 "버그" 로그 전부 | **2~6 m/s (7~22km/h)** | **drvTq −200~−300, 핸들 강하게 잡고 유턴/좁은회전 반복** | 0 (대부분) |

→ 이후 로그는 **(a) 저속 + (b) 운전자 강개입**이 동시에 깔려 있다. 이 두 조건은 **그 자체로 ToiActive=0을 만드는 정상 거동**이다:
- **(a) 저속 LKAS 락아웃**: 다수 현대/기아 MDPS는 일정 속도(대략 ~10~20km/h) 미만에선 LKAS 토크를 아예 안 받는다. 7~22km/h는 그 경계.
- **(b) 운전자 우선**: 운전자가 컬럼토크를 강하게 주면 MDPS는 overlay를 양보(ToiActive=0). 이건 안전상 정상.

**즉 지금 로그의 ToiActive=0 대부분은 "버그"가 아니라 "저속+운전자개입의 정상 양보"일 가능성이 높다.** 실제 온로드 증상("40~60km/h 주행 중, 손 떼고, 회전 직후 조향이 빠짐")과 같은 조건의 로그가 **아직 한 번도 없다.** 이게 분석을 막는 1차 원인이다.

## 2. 근본원인 후보 (증거기반 랭킹)

### H1. (가장 유력) MDPS가 강한 운전자 개입 후 재engage를 못 하고 latch — 단, "정상 속도에서도" 그러는지 미확인
- **증거 for**: 증상 묘사("좌/우회전·유턴 후 多, 핸들 흔들면 복귀")가 전형적 override-후-재engage 실패. 최초 로그처럼 정상속도+손뗌이면 ToiActive=1로 작동함 → 영구결함은 아님(상태의존).
- **증거 against / 불확실**: 현재 "버그" 로그가 전부 저속이라, 저속 락아웃과 구분 불가. 정상속도에서 같은 일이 나는지 **데이터 없음**.
- **확정 실험**: §4의 깨끗한 로그.

### H2. 저속 LKAS 락아웃 / `minSteerSpeed` 설정 불일치 (펌웨어/핑거프린트 관련)
- KIA_EV_SK3엔 `MIN_STEER_*` 플래그 **없음**(다른 일부 현대차엔 `MIN_STEER_32_MPH` 존재). 만약 **이 실차 MDPS가 실제로는 더 높은 최저조향속도**를 요구하는데 OP는 0으로 알고 있으면 → 저속에서 OP가 토크를 보내도 MDPS가 무시(ToiActive=0). 이게 저속 로그를 그대로 설명.
- **이건 "버그"라기보다 설정 문제**일 수 있다. 단, 온로드 정상속도 증상은 이걸로 설명 안 됨.
- **확인법**: 정상속도 로그에서 ToiActive가 잘 1로 붙는지. + 차종 펌웨어 핑거프린트가 KIA_EV_SK3로 정확히 잡혔는지(아래 §3).

### H3. 컬럼토크 센서 오프셋/노이즈로 MDPS의 "운전자 잡고있음" 내부판정이 latch
- **증거 for**: 로그에서 **손 뗐는데도(prs=0) drvTq가 ±50~130로 출렁임**(예: t=52 prs=0 drvTq=128). MDPS가 자기 내부 컬럼토크로 "운전자 개입"을 계속 판정하면 overlay 재개를 미룬다. "핸들 흔들면 복귀"="센서값을 한번 흔들어 임계 아래로 떨어뜨림"과 일치.
- **확인법**: 정상속도 직진 손뗌 구간에서 `CR_Mdps_StrColTq`(drvTq)의 **정지 오프셋/노이즈 폭**과 ToiActive 상관.

### H4. 토크 포화(outTq=±409)가 MDPS를 보호상태로 빠뜨림
- **증거 for**: 유턴 중 `outTq=-409`(STEER_MAX 풀포화) 관측(t=34~35). 구형 MDPS가 지속 최대토크를 받으면 일시 거부할 수 있음.
- **증거 against**: 포화는 큰 회전에서만, 직진 저토크 구간에서도 ToiActive=0이라 단독 원인은 아님. **보조요인**일 수 있음.
- **부작용 적은 방향**: (확정 후) 회전 시 STEER_MAX/rate 소폭↓.

### H5. stock LKAS 카메라 미차단 → LKAS11 이중송신/충돌
- 롱컨개조 차에서 stock 카메라가 버스에 살아 LKAS11을 같이 쏘면 MDPS가 둘을 번갈아 받아 거부/요동. (upstream에 "Reject alternating Hyundai steering torque noise"류 처리가 있는 이유)
- **확인법**: cabana/raw로 **bus0와 bus2에 LKAS11(0x340)이 둘 다 뜨는지**, 카운터/체크섬 충돌 여부.

### H6. (배제) 내 재latch 코드 / OP측 출력문제
- 재latch는 역효과로 **이미 revert**. OP 출력(outTq)은 정상으로 확인됨 → "OP가 토크를 안 쏜다"는 배제됨. 남은 건 **MDPS측 수용 문제**.

## 3. 핑거프린트/환경 점검 (사용자 요청 — 구체적 확인 항목)

> 평소 조향이 되는 것으로 보아 "완전 오인식"은 아닐 가능성이 크지만, **경계 케이스(연식/트림/펌웨어)** 가 미묘한 차이를 만들 수 있다. 아래는 SSH로 확인 가능.

1. **확정된 핑거프린트 확인**: 디바이스에서 `Params`의 `CarParamsPersistent`/`car_fingerprint` 또는 로그의 `carParams.carFingerprint`가 `KIA_EV_SK3`인지. (다른 Soul/Niro EV로 잡히면 STEER_MAX·체크섬·버스가 어긋남)
2. **FW 핑거프린트**: 같은 SK3라도 MDPS FW 버전이 openpilot DB와 다르면 거동 차이 가능. `carParams.carFw`의 MDPS 엔트리 확인.
3. **`MIN_STEER` 요구**: 실차가 저속에서 LKAS를 안 받으면 → KIA_EV_SK3에 최저조향속도 특성이 빠진 것일 수 있음(H2). 정상속도 로그로 판별.
4. **버스 구성**: MDPS12(0x251) 수신, LKAS11(0x340) 송신이 **bus 0**인지. 하네스(hyundai_c)·MANDO_RADAR 유무. (KIA_EV_SK3는 MANDO_RADAR 플래그 없음 — 실차에 만도레이더가 있으면 불일치)
5. **stock 카메라/LKAS 상태**: 롱컨개조 시 카메라가 어떻게 처리됐는지(차단/포워드). H5와 연결.
6. **CHECKSUM**: CRC8 정상 확인됨(코드). 다만 카운터(`CF_Lkas_MsgCount = frame % 0x10`)가 stock과 충돌 없는지(H5와 함께).

## 4. 근본원인을 가르는 "깨끗한 실험" (이거 하나면 대부분 갈림)

지금 로그는 저속+개입으로 오염됨. **아래 조건의 로그 1개**면 H1~H3를 분리 가능:

> **정상 주행속도(40~60km/h), 손 완전히 뗀 상태로, 직진~완만한 코너를 ToiActive=1(정상 조향)로 달리다가 → 자연스럽게 조향이 빠지는 순간**까지를 담기.

판독 기준:
- **그 속도대에서도 ToiActive=0이 손뗌·저토크인데 지속** → H1(진짜 재engage 실패) 확정. 그때 `outTq`/`drvTq 오프셋`/직전 포화여부로 H3·H4 가린다.
- **속도만 올리면 ToiActive가 잘 1로 붙고, 저속에서만 0** → H2(저속 락아웃/설정). 이건 코드/설정으로 깔끔히 처리 가능.
- **빠질 때 항상 직전에 운전자 강개입(drvTq 큼)이 선행** → 정상 양보였고, 진짜 버그는 "재engage 지연 시간"의 문제 → H3 위주.

추가로 한 번, **정차~출발 직진에서 손 떼고** ToiActive가 속도 몇 km/h에서 0→1로 붙는지만 봐도 H2(저속 임계)가 바로 나온다.

## 5. 결론 / 다음 행동 (성급한 패치 금지)

- **코드 변경 안 함.** 지금 단계는 "원인 확정"이지 패치가 아니다.
- 확정 전 손대면 안 되는 이유: 요청비트/ToiFlt 토글은 이미 역효과 확인. 토크/속도/설정도 원인을 모른 채 바꾸면 같은 실수 반복.
- **필요한 것 단 하나**: §4의 정상속도·손뗌 로그 1개(+ §3 핑거프린트/FW 확인값).
- 그게 나오면:
  - H2(저속/설정)면 → `minSteerSpeed`/플래그 정합 (부작용 거의 없음, 원천적).
  - H3(센서 latch)면 → 재engage 판정에 컬럼토크 노이즈 마진/디바운스 (토글 아님).
  - H4(포화)면 → 회전 시 토크상한 소폭↓.
  - H1 단독이면 → 위 조합 + 신중한 재engage 보조(단, ToiFlt 유발 안 하는 방식으로).
